Fission Of Soul

Fission Of Soul (FOS) is a small general-purpose C library providing generic containers, strings, pseudo-random number generation, arbitrary-precision integers, hashing, and other reusable low-level facilities.

FOS is written in C11 and is designed to be easy to integrate into existing C projects. It uses a small number of dependencies and provides explicit, straightforward interfaces without requiring a runtime environment or framework.

FOS is primarily intended for Windows, but the source code can also be built on other platforms with a suitable C11 compiler.

Features

The library currently provides:

  • FOS_Bignum — arbitrary-precision integer arithmetic.
  • FOS_HashMap — generic hash map using open addressing and linear probing.
  • FOS_Heap — generic binary min-heap and priority queue.
  • FOS_List — generic singly-linked list with a tail pointer.
  • FOS_Memory — configurable memory allocation backend.
  • FOS_Queue — generic FIFO queue implemented using FOS_List.
  • FOS_Rng — PCG-based pseudo-random number generation.
  • FOS_Set — generic unordered set implemented using FOS_HashMap.
  • FOS_Stack — generic LIFO stack implemented using FOS_List.
  • FOS_String — owned strings and non-owning string slices.
  • FOS_Vec — generic dynamic array with optional type-specific wrappers.

The library is modular. Individual modules can be included independently, while FOS.h provides an umbrella header for programs using multiple modules.

Design philosophy

FOS favors explicit, lightweight interfaces and conventional C data structures.

The library does not attempt to hide the nature of its data structures. Containers expose straightforward operations and document their complexity, ownership requirements, and failure behavior.

FOS is generic where useful, primarily through element sizes, function pointers, and C macros.

Memory allocation is routed through FOS_Memory, allowing applications to replace the default C allocation functions with a custom allocation backend.

Higher-level containers may be implemented in terms of simpler FOS modules where this provides a small and practical implementation. For example:

FOS_Queue -> FOS_List
FOS_Stack -> FOS_List
FOS_Set   -> FOS_HashMap
FOS_Heap  -> FOS_Vec

Requirements

FOS requires a compiler supporting C11.

For Windows builds using CMake, the requirements depend on the selected compiler. The Microsoft Visual C workflow uses the normal Visual Studio CMake generator. GCC and Clang can be used with Ninja, while Pelles C requires its environment setup script and Ninja.

The following compilers are supported by the provided CMake configuration:

  • Microsoft Visual C (MSVC)
  • GCC
  • Clang
  • Pelles C

The supplied CMake project requires CMake 4.0 or newer. Pelles C support in CMake may require a newer CMake version depending on the installed toolchain.

Including FOS

The complete public interface can be included through the umbrella header:

#include "FOS.h"

Individual modules can also be included separately:

#include "FOS_Vec.h"
#include "FOS_HashMap.h"

Using individual headers is useful when only a subset of the library is required.

Minimal example

The following program creates a type-specific vector of int, adds two elements, and prints them:

#include "FOS.h"
#include <stdio.h>

FOS_VEC_DEFINE(int, int)

int main(void)
{
    FOS_Vec_int vec = FOS_vec_int_new();

    if (!FOS_vec_int_push(&vec, 10) ||
        !FOS_vec_int_push(&vec, 20))
    {
        FOS_vec_int_free(&vec);
        return 1;
    }

    FOS_VEC_FOR_EACH(const int, &vec, value)
        printf("%d\n", *value);

    FOS_vec_int_free(&vec);

    return 0;
}

The example uses only the public API. The underlying representation of FOS_Vec is not accessed directly.

Building on Windows with CMake

CMake is the recommended way to build FOS on Windows.

The FOS project defines a static library target named FOS and requests the C11 language standard.

Microsoft Visual C

CMake normally uses a Visual Studio generator and the MSVC toolchain by default on Windows.

From a Visual Studio Developer Command Prompt, configure the project with:

cmake -S . -B build

Then build it with:

cmake --build build --config Release

No Ninja installation is required for the normal MSVC workflow.

The MSVC build uses warning level 4:

/W4

GCC

To build with GCC, GCC and Ninja must be available through PATH.

Configure the project with:

cmake -S . -B build-gcc -G Ninja -DCMAKE_C_COMPILER=gcc

Then build it with:

cmake --build build-gcc

The GCC build enables:

-Wall -Wextra -Wpedantic

Clang

To build with Clang, Clang and Ninja must be available through PATH.

Configure the project with:

cmake -S . -B build-clang -G Ninja -DCMAKE_C_COMPILER=clang

Then build it with:

cmake --build build-clang

The Clang build enables:

-Wall -Wextra -Wpedantic

Pelles C

Before configuring the project with Pelles C, run the povars64.bat script supplied with the Pelles C installation. It is recommended to use plain cmd.exe for that purpose (not PowerShell).

Ninja must also be available through PATH.

After running povars64.bat, configure the project with:

cmake -S . -B build-pelles -G Ninja -DCMAKE_C_COMPILER=pocc

Then build it with:

cmake --build build-pelles

The Pelles C build selects the multithreaded runtime with:

-MT

Pelles C support was added to CMake relatively recently and may require a newer CMake version than the general minimum declared by the FOS project. The project deliberately retains a lower general cmake_minimum_required() value so that valid builds with other supported toolchains are not unnecessarily excluded.

Build directories

When using multiple compilers, use a separate build directory for each toolchain:

build/
build-gcc/
build-clang/
build-pelles/

A build directory configured for one toolchain should not be reused for another.

CMake target

The project defines a static library target named:

FOS

The target contains all FOS implementation files and publishes the project's include directory as a public include directory.

The library requires C11, which is requested by the CMake configuration with:

target_compile_features(FOS
    PUBLIC
        c_std_11
)

Applications using CMake can add the FOS source tree to their own project with add_subdirectory() and link against the FOS target.

For example:

cmake_minimum_required(VERSION 4.0)

project(MyProgram C)

add_subdirectory(path/to/FOS)

add_executable(my_program
    main.c
)

target_link_libraries(my_program PRIVATE FOS)

The application can then be configured and built with the generator appropriate to the selected toolchain.

Building manually

CMake is not required to build FOS.

On Unix-like systems, the source files can be compiled directly with GCC:

gcc -std=c11 -Wall -Wextra -Wpedantic -O2 -Iinclude -c src/*.c

The resulting object files can then be combined into a static library:

ar rcs libfos.a *.o

The resulting static library can be linked into applications using the appropriate compiler and linker options for the target platform.

Individual FOS source files may also be compiled directly together with an application when a separate static library is unnecessary.

Memory allocation

FOS modules use the allocation functions provided by FOS_Memory rather than calling malloc(), free(), realloc(), and calloc() directly.

The default backend uses the corresponding functions from the C standard library.

Applications may replace the allocator backend when a custom allocation strategy is required.

Because the allocator backend is global, changing it affects all FOS operations that use FOS_Memory.

Error handling

FOS generally reports operational failures through return values.

Functions returning bool use true for success and false for failure.

Functions returning pointers generally use NULL to indicate failure.

Functions returning structures may return a zero-initialized object when construction or allocation fails.

Functions returning size_t may use SIZE_MAX as an error or "not found" sentinel where documented by the corresponding module.

Individual module documentation specifies the exact behavior of each function.

Ownership

FOS containers generally own storage allocated for their elements.

For example, when an element is inserted into FOS_Vec, FOS_List, FOS_HashMap, or FOS_Set, the element's bytes are copied into container-owned storage.

FOS does not generally perform deep copies of resources contained within an element. If an element contains pointers or other resources, the pointer values themselves may be copied while the objects they refer to remain under the caller's control.

The individual module documentation describes the precise ownership rules for each container.
